Encoded-witness recomposition experiment
=======================================

The repeated-recomposition hypothesis is confirmed for this relation. The
prototype is mathematically equivalent, and materially faster in complete PiCCS
proofs, including inputs from later lifecycle states. It does not change the
relation, commitments, packing, transcript, sumcheck, or verifier.

What factorization actually exists
---------------------------------
package/assignment_transport.rs retains field values as 41 balanced base-3
coordinates. package/matrix_program/form.rs::retained emits a geometric run with coefficient 1 and ratio 3; singleton
coordinates have ratio 1. Matrix affine operations scale and combine these runs.
No dense expanded matrix is materialized by the production path, but arithmetic
still expands each run while computing a row dot product:
  superneo_eval/geometric.rs::geometric_dot_real
  superneo_eval/geometric.rs::geometric_weighted_projection

For a distinct run q=(start,len,ratio), define
  (D_run x)[q] = sum_{j=0}^{len-1} ratio^j x[start+j].
Let L put each run occurrence's scalar coefficient in its matrix row. Then
  M_encoded x = L (D_run x)
exactly, over F and over K. This statement needs no witness-specific zeros,
constraint satisfaction assumption, or approximate arithmetic. The prototype
uses the actual run boundaries, including those crossing 54-lane packing blocks.
It does not infer logical wires from physical row numbers.

Measured structure (all snapshots share the same relation):
  run occurrences across four matrices       38,533,993
  distinct (start,length,ratio) runs           1,070,525
  distinct length-41 runs                     1,067,152
  distinct singleton runs                         3,373
  digit visits in occurrence expansion    1,541,414,313
  digit visits in shared reconstruction      43,756,605
That is 35.23x fewer digit visits. The retained logical affine expressions still
contain 38.5 million references; this prototype does not deduplicate entire
expressions, Poseidon round templates, or common affine subexpressions.

Fresh path: reconstruct each unique run from the packed signed-unit masks using
Horner evaluation over F, then evaluate the four logical affine matrices. The
production comparison uses its existing parallel matrix/chunk schedule on the
same already-created MatrixWindow, with four workers in both variants.

Carried path: preserve fill_combined_projection exactly. It combines all running
sources with their gamma powers and applies the required ring-coefficient weights.
Only then apply D_run to that K-valued projected vector and evaluate L. Matrix
weights, padding projection, matrix shift, and trimming remain the production
operations. Reconstructing Dw from a fresh scalar witness and substituting it
for this ring projection would be incorrect: the projection mixes lanes inside
54-coefficient ring blocks, while the digit decomposition uses 41 coordinates.

The test-only complete-proof backend initializes the ordinary CPU oracle with
these equivalent fresh and carried tables. Every subsequent sumcheck operation,
norm constraint, equality weight, binding, opening, and verifier is unchanged.
Production constructs a fresh matrix window and, when needed, another for carried
evaluation. The prototype needs neither for those two evaluations, but its final
openings still construct the original MatrixWindow. That cost is included in the
complete-proof measurements. The baseline retains its fresh window for openings.

Measurement method
------------------
Microbenchmarks: one warmup + five measured repetitions, alternating generic and
factored order; allocations of output/recomposition vectors included. Relation
loading, matrix-window construction, plan construction, equality assertions and
satisfaction checks are outside those kernel timings. Outputs are consumed.

Complete PiCCS: one warmup pair + three measured pairs, alternating variant order.
The timer includes all ordinary proving work and backend construction; excludes
loading captured data, preparing the reusable relation plan, and verification.
Every produced proof is verified outside the timer. Every pair has exactly equal
serialized output claims and sumcheck-round coefficients (the entire PiCCS proof
payload). This is an equivalent implementation, not an ablation.

The retained plan setup cost is reported separately; adding it back gives a cold
single-proof estimate. It can be amortized across repeated folds of this fixed
relation. No benchmark processes ran concurrently. All test processes have an
unconditional 300-second process-group timeout; all successful runs finished
below that cap. Raw JSONL files retain min/max variability and individual samples.

Interpretation
--------------
The large gain comes from avoiding repeated reconstruction, not from the earlier
zero-pattern sumcheck specialization. Fresh arithmetic improves roughly 16-19x;
the carried matrix-application stage improves roughly 19-21x. Complete PiCCS
improves roughly 29-33% with a reusable plan, including later folds. Its remaining
time is substantial because ring projections, norm sumcheck, full ring openings,
and ordinary matrix-window construction still execute.

This warrants production integration of shared run reconstruction, provided the
relation representation owns its memory and its setup is amortized. The test-only
backend is an experimental proof of the benefit, not a proposed public API.
The next measured targets are the two carried ring projections (about 1.7-2.0 s)
and full-opening contractions (about 1.2-1.5 s on later snapshots). The two
projections rebuild the same gamma-weighted source combination before applying
different ring forms; sharing that combination is a concrete next experiment.
This run does not claim a measured gain for such fusion or for shared affine DAGs.

Final-opening reuse and its limits
---------------------------------
The experiment checks that each of the four fully bound fresh scalar tables
matches eval_a[matrix][0] from the full production opening. It also checks that
each fully bound assignment matches that source's eval_k[0]. These are already
available and do not need recomputation as scalar values.

However, each nonzero source needs 54 coefficients for each of four matrix
openings and 54 padding coefficients: 270 K values, not five scalar values.
The scalar sumcheck tables retain only coefficient zero. The carried table is a
single gamma-weighted combination of source/matrix/coefficient openings; its
one final scalar does not separate those outputs. Zero sources are already skipped.

Consequently, reusing these scalar entries does not eliminate the dominant ring
opening pass. The diagnostic split below reproduces every coefficient exactly.
No performance gain is claimed for scalar reuse; we checked availability, rather
than disabling remaining coefficients and calling that equivalent.

Production already avoids a second digit-by-occurrence expansion in openings:
geometric.rs::add_geometric_events emits start/end events, and row_forms.rs
resolves the shared-ratio recurrence into packed ring forms. The contraction
parallel.rs::eval_active_blocks_many then applies these forms to active witnesses.
Padding openings already exploit repeated 54/64-lane phase templates. Completed
carried storage is reused for opening scratch, and a complete fresh matrix window
is reused when available. These optimizations materially limit the additional
benefit of simply retaining scalar sumcheck values.

Retaining all 54 coefficients as row tables for the four matrices would take
3,470,276,736 bytes (3.23 GiB) per source before padding and other state. Doing
that for eight active sources would exceed this machine's 24 GiB by itself.
No such richer-table prototype was implemented; a narrower compressed or
relation-specific representation would need a separate experiment.

Memory and integration limits
-----------------------------
The reusable experimental plan retains 674,368,688 bytes (643.13 MiB): run keys,
row offsets, and (run-id,coefficient) occurrences. Original MatrixWindow storage
is 957,308,056 bytes (912.96 MiB). A temporary distinct-run value array uses
8,564,200 bytes for F, or 17,128,400 bytes for K. Fresh table storage is unchanged
at 64,264,384 bytes. The projected vector/opening scratch is 703,420,416 bytes.

These are allocation payloads, NOT measured peak RSS. Plan construction also
has a temporary HashMap and vector growth capacity. During prototype openings,
the plan remains alive alongside the original window and scratch: approximately
2.335 GB of those three payloads, versus 1.661 GB without the plan, excluding
witnesses/allocator overhead. The 1 GiB window-budget parameter is unchanged,
but the prototype's plan is outside that budget. It is not a demonstration of
a production implementation fitting all additional memory into 1 GiB.

A production integration must account for or replace that retained matrix data,
ideally owning the factorization as the relation's evaluation representation.
It should avoid adding a second large independent cache with unclear lifetime.
This experiment does not change the verifier or claim a full lifecycle speedup:
commitment generation, recursive witness execution, other reductions, and final
lifecycle verification were not replaced. Complete PiCCS and real later-fold
inputs are measured, rather than extrapolating initial-fold microbenchmarks.

Reproduction
------------
From the repository root (Rust toolchain and dependencies already installed):

  python3 experiments/sumcheck-specialization/fetch_artifacts.py
  cargo build --release -p nightstream --bin nightstream-poseidon2-bench
  target/release/nightstream-poseidon2-bench compile --output /private/tmp/nightstream-specialization.nsc
  python3 experiments/recomposition/run.py capture
  python3 experiments/recomposition/run.py measure --step 1
  python3 experiments/recomposition/run.py measure --step 2
  python3 experiments/recomposition/run.py measure --step 3
  python3 experiments/recomposition/run.py proofs --step 1
  python3 experiments/recomposition/run.py proofs --step 2
  python3 experiments/recomposition/run.py proofs --step 3
  python3 experiments/recomposition/summarize.py
  python3 experiments/recomposition/run.py checks

run.py accepts --package and --directory for alternative scratch locations. It
caps each cargo-test process, including compilation, at 300 seconds and kills
the entire process group on timeout. The package compiler is an ordinary build
utility, not a test invocation. Capture files remain in /private/tmp to avoid
checking hundreds of megabytes into the repository. The original LFS pointers
were restored after measurements; fetch_artifacts.py rehydrates verified content.

Experimental code (all paths relative to repository root):
  crates/nightstream/tests/experiments/recomposition_capture.rs
  crates/neo-reductions/tests/experiments/recomposition.rs
  crates/neo-reductions/tests/experiments/recomposition_proof.rs
  crates/neo-reductions/tests/experiments/recomposition_openings.rs
The recomposition module is nested under the earlier specialization experiment
to reuse its package MatrixRows adapter and access private CPU-oracle tables.
Only cfg(test) module hooks are added to production source files. The earlier
dev dependency and experiments are retained. No production backend is selected
or modified by these changes.
